# EKS Namespace Access Pattern

The source module attempted to coordinate EKS access entries, Kubernetes Roles/RoleBindings, and namespace creation for read/write groups. Its intended model is retained here: explicit permission type, namespace-scoped resources, and an EKS identity entry tied to an IAM principal.

The original access-entry count expression mixed `can(index(...))` with map lookup and could create incorrect resource counts; namespace creation used `local-exec kubectl`, which bypassed Terraform resource ownership. Rebuild with validated `permission_type` values (`read`, `write`, `read-write`), conditional `aws_eks_access_entry` resources, native `kubernetes_namespace`, and native Role/RoleBinding resources. Avoid the broad resource list from the source example: request only the API resources needed by the namespace team, and never grant Secret read access as part of a generic read role.

The module now implements the corrected design: an EKS access entry maps the IAM principal into a dedicated Kubernetes group; native Kubernetes resources create the namespace, namespaced Role, and RoleBinding. It intentionally excludes Secret reads, cluster-wide privileges, and namespace creation through `local-exec`.

Use EKS authentication mode that supports access entries and configure the Kubernetes provider with a short-lived, role-based identity that can manage the target namespace. Review the API resource list against the team's actual deployment workflow before broad use. The group name generated by this example is a stable convention and must not collide with groups managed elsewhere.
